# Security

## Reporting a vulnerability

Please report security problems privately. Do not open a public issue or
pull request for them.

> **CONTACT PLACEHOLDER. Maintainer: replace this block with the address or
> private reporting channel to use, before publishing this file.**
>
> Report to: `<security contact to be filled in>`

Include, as far as you can:

- what is affected (data plane, control plane, a tool, the container
  setup) and the commit you looked at;
- how to reproduce it, ideally against the mock providers
  (`config/omnigate.dev.json`, `tools/e2e.py`);
- what an attacker gains.

Please do not test against deployments you do not own, and do not include
real provider keys, gateway keys or tokens in a report.

No release has been tagged yet. Fixes are made on `main`. Whether fixes
will also be applied to earlier releases, once there are any, has not been
decided; the release process is in [docs/releasing.md](docs/releasing.md).

## Security model in brief

omnigate is two processes. The **data plane** is the public port that
applications call. The **control plane** holds configuration, gateway keys,
the usage ledger, media jobs and the dashboard, and is meant to stay on a
private network behind a TLS proxy. See
[docs/architecture.md](docs/architecture.md).

### Three credentials, three audiences

| Credential | Held by | Sent as | Opens |
|---|---|---|---|
| Gateway key | Applications | `Authorization: Bearer` or `x-api-key`, to the data plane | Text endpoints, the jobs API and file downloads, within that key's model list, rate limit and budget |
| Internal token (`OMNIGATE_INTERNAL_TOKEN`) | The two processes | `x-omnigate-internal`, from data plane to control plane | `/internal/*` on the control plane: the config snapshot, usage and refusal-count intake, the forwarded jobs API |
| Admin token (`OMNIGATE_ADMIN_TOKEN`) | Operators | `Authorization: Bearer`, or once as the dashboard password | The dashboard, `/admin/*` (which includes creating and revoking gateway keys) and `/metrics` on the control plane |

None of them works in another's place.

- **Gateway keys** are stored and compared as SHA-256 hashes; the data
  plane only ever receives hashes. A key written in the config file can be
  given as its hash (`key_sha256`). A key created through the admin API or
  the dashboard is generated by the control plane (32 random bytes), shown
  once, and kept only as its hash. A key can be limited to a list of
  models, a request rate and a budget (over everything it ever spent, per
  UTC month or per UTC day), disabled, rotated and deleted; a disabled,
  deleted or rotated-away key is refused as an unknown key.
- **The internal token** is compared in constant time. Neither process
  starts without it; an empty value counts as not set.
- **The admin token** is never open by default: if it is not set, a random
  one is generated at startup and written to the log. The dashboard
  exchanges it for a signed session cookie (12 hours, `HttpOnly`,
  `SameSite=Strict`, `Secure` when reached over TLS), so the token itself is
  sent once. Five failed logins from one address lock that address out for a
  minute.
- **Changes from a browser session need a CSRF token.** A `POST`, `PATCH` or
  `DELETE` on `/admin/*` (and the sign-out) that is authenticated by the
  session cookie must carry a token derived from that session, in the
  `x-csrf-token` header or the `_csrf` form field. Requests authenticated by
  the bearer token are exempt, because a browser never attaches that header
  by itself. See [docs/admin.md](docs/admin.md#csrf-scripts-and-browsers).
- **The dashboard loads nothing from elsewhere.** Its styles and script are
  inline and allowed by a per-response nonce in the
  `Content-Security-Policy`; the pages also forbid framing and are not
  cached.
- **Admin actions are recorded.** Key changes, sign-ins (successful, denied
  and throttled) and sign-outs are appended to an audit log with the time,
  how the caller was authenticated and the peer address, never with a
  secret. See [docs/admin.md](docs/admin.md#the-audit-log).
- **The control plane refuses what it does not recognise.** A request path
  that contains a percent-encoded character, a backslash, a NUL byte or a
  `.` or `..` segment is answered `400` before anything else looks at it,
  so the credential checks and the router always see the same path. The
  first path segment decides which credential is needed, and a segment the
  control plane does not serve is a `404` at that check, so a route added
  later stays closed until it is deliberately opened. Credentials are
  checked before a request body is read. This is the fix for the first
  entry under [Past advisories](#past-advisories).

### Provider secrets

- Provider keys, bucket credentials and (optionally) webhook secrets are
  read from environment variables. The config file only names the variables.
- Text provider keys exist only in the data plane's environment; media
  provider keys and bucket credentials only in the control plane's.
- The config snapshot sent to data planes contains no budgets, no prices and
  no secrets.
- Requests that carry a provider key do not follow redirects.
- Of a provider's response headers, only an allowlist reaches the client:
  retry hints, rate-limit counters and request ids. Cookies, organization
  and project headers and everything else are dropped. Note that the
  rate-limit headers describe your provider account's limits and are
  visible to every application that holds a gateway key.

### Isolation between gateway keys

- A key sees only its own media jobs and files (also across a rotation of
  that key).
- The text response cache is per key: the gateway key is part of what
  identifies a cached request, and a hit is served only after
  authentication, the budget, the model list and the rate limit have been
  checked.
- The **media output cache is shared across keys**; see Known limits.

### Files and webhooks

- Outputs on local disk are served through URLs signed with HMAC-SHA256 that
  expire (one hour by default), or to the gateway key that owns the job.
  The signing key is `OMNIGATE_SIGNING_SECRET`, or is derived from the
  internal token.
- Outputs in a bucket are assumed private and handed out as presigned URLs.
- Webhooks are signed the [Standard Webhooks](https://www.standardwebhooks.com/)
  way (HMAC-SHA256 over id, timestamp and body). Receivers should verify the
  signature and the timestamp; see [docs/api.md](docs/api.md#webhooks).
- Webhook URLs must be http(s), without embedded credentials, and must not
  resolve to loopback, private or link-local addresses unless
  `media.webhooks.allow_private` is set. For each delivery the host is
  resolved once, every resulting address is checked, and the connection is
  made to the checked address, so a DNS answer that changes between the
  check and the call (DNS rebinding) cannot point a delivery at an internal
  address. Redirects are not followed.

### Resource limits on the public port

- A request body may be at most 8 MiB.
- A client that does not finish sending a request, or leaves a connection
  idle, is disconnected after `OMNIGATE_CLIENT_TIMEOUT_MS` (30 seconds).
- A response that stops moving, because the upstream went silent or the
  client stopped reading, is cut off after
  `OMNIGATE_STREAM_IDLE_TIMEOUT_MS` (5 minutes).
- At most `OMNIGATE_MAX_CONNECTIONS` (4096) connections are served at once;
  further ones get an immediate 503.
- Requests the gateway refuses are counted per key name and reason, with a
  cap on the number of distinct series, so a flood of made-up keys cannot
  grow memory.

These bound what one client can hold; they are not a defence against a
volumetric attack. Put the data plane behind a proxy or load balancer that
you would trust with that.

### What must stay private

- The control plane's port. Expose the dashboard only through a TLS proxy
  that refuses `/internal/*` from outside, as `deploy/Caddyfile` does.
- Both tokens, the `.env` file, and the config file if it holds raw keys or
  inline webhook secrets.
- The control plane's data directory: the ledger files (`ledger.jsonl`,
  its sealed segments and its two snapshots) and `jobs.jsonl` (usage per
  key; job inputs, metadata and webhook URLs), `keys.json` (key hashes, and
  the webhook secret of any managed key that has one, in clear text),
  `audit.jsonl` and its rotated files (who did what, from which address),
  and the media directory or bucket.
- The control plane's log, if you let it generate the admin token.

The data plane's access log holds key **names**, route names and request
paths, never keys, key hashes or request bodies.

Details: [docs/deployment.md](docs/deployment.md#what-to-keep-private).

## Known limits

These come from the code and from the README's
[Known limits](README.md#known-limits) section. They are known, not
vulnerabilities to report.

- **No TLS listener on either process.** The included Caddy proxy (or
  another) provides it. Data-plane-to-control-plane traffic over HTTPS is
  untested; keep it on a private network.
- **One shared admin token.** No user accounts or roles, so the audit log
  can say how a caller was authenticated and from which address, not who
  they were. Sessions cannot be revoked individually; changing the token
  ends all of them. Whoever holds the token can create gateway keys.
- **The audit log is a plain file** the control plane appends to. It is not
  tamper-evident, and someone who can write to the data directory can
  change it. If a line cannot be written, the action still goes ahead (and
  an error is logged). Reads of the admin API are not recorded, and neither
  are requests refused for a missing token or CSRF token. The file is
  rotated by size and only three older files are kept, so old entries are
  eventually deleted; copy it elsewhere if you need a longer record.
- **A managed key's webhook secret is stored in clear text** in `keys.json`,
  because signing needs the secret itself.
- **The login lockout counts per client address and lives in memory.**
  Behind a reverse proxy all clients share one address.
- **Budgets are enforced after the fact**, with up to one poll interval of
  lag, and cannot newly block a key during a control-plane outage. A
  monthly or daily budget unblocks by itself when its UTC period turns; a
  total budget never resets.
- **The internal token is as powerful as every gateway key together.** On
  `/internal/*` it reads the config snapshot (key hashes, upstream
  addresses), writes usage events, and acts as any gateway key on the jobs
  API. Keep the control plane's port private.
- **Key changes take effect at the next config poll**, a couple of seconds
  by default. A data plane that cannot reach the control plane keeps
  accepting a key that was revoked in the meantime, until it can poll
  again.
- **Rate limits are per data-plane process** and reset on restart.
- **The media output cache is shared across gateway keys.** An identical
  cacheable job request from another key reuses the stored output.
- **Output downloads send no provider credentials**, and follow redirects.
- **Refusal counts and the access log are for diagnosis, not for audit**:
  the counts are best effort and kept in memory only.
- **Nothing has run under production load.**

## Past advisories

No release has been tagged, so these are identified by commit.

### Authentication bypass on the control plane through percent-encoded paths

Fixed in commit 97cf396 (November 2026). Found by an independent review of
the code, not by a report of abuse.

**What was wrong.** The control plane's credential checks compared the
request path as it was sent, while its router matched the percent-decoded
path. A request whose first path segment was written with an encoded
character (`/%61dmin/keys` for `/admin/keys`, `/%69nternal/config`,
`/%6Detrics`) was not recognised by the admin-token check, the
internal-token check or the CSRF check, and still reached the handler.

**What it allowed.** Anyone who could send HTTP requests to the control
plane, without any credential, could:

- use the whole admin API: list keys and usage, create, change, disable,
  rotate and delete managed gateway keys, read the overview and the audit
  log;
- read `/metrics`;
- use `/internal/*`: read the config snapshot (key hashes, upstream names
  and addresses), write usage events into the ledger, and read, create and
  cancel media jobs as any gateway key.

It did not reveal the admin token, the internal token or any provider key;
no endpoint returns those.

**Who was affected.** Every commit before 97cf396 that has an admin token
(before commit c53acd6 the admin API had no authentication at all), if the
control plane's port could be reached by someone you do not trust. That
includes the Compose deployment when the dashboard's host name was
reachable from outside: the included proxy forwards the dashboard host's
requests to the control plane as they are, so it was no protection for the
admin API. A control plane bound to loopback or reachable only from a
trusted network was not exposed. The data plane's port was not a way in:
it forwards only `/v1/jobs*` and `/v1/files/*`.

**What to do.**

1. Update the control plane to 97cf396 or later.
2. List the keys (`GET /admin/keys`) and delete any managed key you did not
   create. Rotate the managed keys you want to keep if they were created or
   rotated while the control plane was exposed.
3. Look through the audit log (it exists from commit 5450398 on) for
   `key.create`, `key.update`, `key.rotate` or `key.delete` entries with
   `"auth": "none"`. Such an entry could only be produced through this
   bypass. Reads were never recorded, so a clean log shows that no key was
   changed this way, not that nobody looked.
4. Treat what the snapshot and the admin API show as disclosed for that
   period: key names and hashes, usage figures, upstream addresses, and
   recent jobs with their signed output links. A generated key cannot be
   recovered from its hash; replace any short or guessable key you wrote
   into the config file yourself.
5. If spend figures from that period matter, remember that usage events
   could have been written without a credential.

**The fix.** A path with any encoded character is refused with `400` before
routing (no route needs one); the checks deny by default, so an unknown
first path segment is a `404` instead of being passed to the router; and
credentials are checked before the body is parsed. Regression tests cover
it at the unit level and in the end-to-end test.
