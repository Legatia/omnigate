# Security

## Reporting a vulnerability

Please report security problems privately. Do not open a public issue or
pull request for them.

> **CONTACT PLACEHOLDER. Maintainer: replace this block with the address or
> private reporting channel to use, before publishing this file.**
>
> Report to: `<security contact to be filled in>`

Include, as far as you can:

- what is affected (data plane, control plane, a tool, the container
  setup) and the commit you looked at;
- how to reproduce it, ideally against the mock providers
  (`config/omnigate.dev.json`, `tools/e2e.py`, `tools/malformed_test.py`);
- what an attacker gains.

Please do not test against deployments you do not own, and do not include
real provider keys, gateway keys or tokens in a report.

No release has been tagged yet. Fixes are made on `main`. Whether fixes
will also be applied to earlier releases, once there are any, has not been
decided; the release process is in [docs/releasing.md](docs/releasing.md).

Operators: the checklist for running this safely is
[docs/security.md](docs/security.md). If you ran a commit older than
3a0b147, read [Past advisories](#past-advisories).

## Security model in brief

omnigate is two processes. The **data plane** is the public port that
applications call. The **control plane** holds configuration, gateway keys,
the usage ledger, media jobs and the dashboard, and is meant to stay on a
private network behind a TLS proxy. See
[docs/architecture.md](docs/architecture.md).

### Three credentials, three audiences

| Credential | Held by | Sent as | Opens |
|---|---|---|---|
| Gateway key | Applications | `Authorization: Bearer` or `x-api-key`, to the data plane | Text endpoints, the jobs API and file downloads, within that key's model list, rate limit, budget and limit on unfinished jobs |
| Internal token (`OMNIGATE_INTERNAL_TOKEN`) | The two processes | `x-omnigate-internal`, from data plane to control plane | `/internal/*` on the control plane: the config snapshot, usage and refusal-count intake, the forwarded jobs API |
| Admin token (`OMNIGATE_ADMIN_TOKEN`) | Operators | `Authorization: Bearer`, or once as the dashboard password | The dashboard, `/admin/*` (which includes creating and revoking gateway keys) and `/metrics` on the control plane |

None of them works in another's place.

- **Gateway keys** are stored and compared as SHA-256 hashes; the data
  plane only ever receives hashes. A key written in the config file can be
  given as its hash (`key_sha256`). A key created through the admin API or
  the dashboard is generated by the control plane (32 random bytes), shown
  once, and kept only as its hash. A key can be limited to a list of
  models, a request rate, a number of unfinished media jobs and a budget
  (over everything it ever spent, per UTC month or per UTC day), disabled,
  rotated and deleted; a disabled, deleted or rotated-away key is refused
  as an unknown key.
- **The internal token** is compared in constant time. Neither process
  starts without it; an empty value counts as not set.
- **The admin token** is never open by default: if it is not set, a random
  one is generated at startup and written to the log. A token that is set
  but shorter than 16 characters stops the control plane from starting.
  The dashboard exchanges the token for a signed session cookie (12 hours,
  `HttpOnly`, `SameSite=Strict`, `Secure` when reached over TLS), so the
  token itself is sent once.
- **Guessing the admin token is throttled, per client address.** Five
  failed sign-ins within a minute lock that address out of the sign-in
  form, and 20 wrong bearer tokens on `/admin/*` or `/metrics` within a
  minute lock it out of bearer access (`429`, the right token included),
  in both cases until the minute is over. A request with no token at all
  is not counted. The address is the connection's, or, with
  `OMNIGATE_TRUST_FORWARDED=1`, the last hop of `X-Forwarded-For`, which is
  only safe when a proxy that writes that header is the only way in. See
  [docs/admin.md](docs/admin.md#two-ways-in).
- **Changes from a browser session need a CSRF token.** A `POST`, `PATCH` or
  `DELETE` on `/admin/*` (and the sign-out) that is authenticated by the
  session cookie must carry a token derived from that session, in the
  `x-csrf-token` header or the `_csrf` form field. Requests authenticated by
  the bearer token are exempt, because a browser never attaches that header
  by itself. See [docs/admin.md](docs/admin.md#csrf-scripts-and-browsers).
- **The dashboard loads nothing from elsewhere.** Its styles and script are
  inline and allowed by a per-response nonce in the
  `Content-Security-Policy`; the pages also forbid framing and are not
  cached.
- **Admin actions are recorded.** Key changes, sign-ins (successful, denied
  and throttled) and sign-outs are appended to an audit log with the time,
  how the caller was authenticated and the peer address, never with a
  secret. See [docs/admin.md](docs/admin.md#the-audit-log).

### Deny by default

Both processes refuse what they do not recognise instead of passing it on.

- **The control plane.** A request path that contains a percent-encoded
  character, a backslash, a NUL byte or a `.` or `..` segment is answered
  `400` before anything else looks at it, so the credential checks and the
  router always see the same path. The first path segment decides which
  credential is needed, and a segment the control plane does not serve is
  a `404` at that check, so a route added later stays closed until it is
  deliberately opened. Credentials are checked before a request body is
  read, and the one body an anonymous caller may send (the sign-in form) is
  limited to 4,096 bytes. The listener speaks HTTP/1.1 only.
- **The data plane.** A request head is validated before anything else
  reads it: a header line without a colon, a bare line feed, a control
  byte, two lengths, a length together with chunked encoding, or a body on
  a method that has none is answered `400`; a body without a length `411`;
  an unknown expectation `417`. A path has exactly one accepted spelling
  (no percent-encoding, no trailing slash, no dot segments), a query string
  a small character set, and JSON at most 64 levels of nesting. See
  [docs/api.md](docs/api.md#request-heads-paths-and-queries).
- **Between the two.** The request the data plane sends to the internal API
  carries the internal token, so the client's share of it is kept narrow:
  a validated path and query, set as separate URL components, and one
  header with a restricted character set. A client cannot make the data
  plane call anything but the jobs and files API.
- **A crash is not silent.** One data-plane process serves every
  connection, so input is validated before any code that could assert on
  its shape; if a panic happens anyway, the process logs one line and exits
  with status 70 for its supervisor to restart.

### Secrets, per process

- Provider keys, bucket credentials and (optionally) webhook secrets are
  read from environment variables. The config file only names the variables.
- Each process holds only what it uses:

  | Process | Holds |
  |---|---|
  | Data plane (faces the internet) | The internal token; text provider keys |
  | Control plane (private) | The internal token; the admin token; media provider keys; bucket credentials; webhook secrets |

  The Compose deployment enforces this with one environment file per
  container (`.env.control`, `.env.dataplane`); the data-plane container is
  given no admin token, media key, webhook secret or bucket credential.
- The config snapshot sent to data planes contains no budgets, no prices and
  no secrets.
- Requests that carry a provider key do not follow redirects.
- Of a provider's response headers, only an allowlist reaches the client:
  retry hints, rate-limit counters and request ids. Cookies, organization
  and project headers and everything else are dropped. Note that the
  rate-limit headers describe your provider account's limits and are
  visible to every application that holds a gateway key.
- A release build of the control plane refuses to start without
  `OMNIGATE_CONFIG`. The development config in this repository has
  published keys and a published webhook secret and allows calls to private
  addresses; it can only stand in for a missing config in a development
  build.

### Isolation between gateway keys

- A key sees only its own media jobs and files (also across a rotation of
  that key).
- The text response cache is per key: the gateway key is part of what
  identifies a cached request, and a hit is served only after
  authentication, the budget, the model list and the rate limit have been
  checked.
- What the data plane learns about a provider model from an error (that it
  rejects sampling parameters, or wants thought signatures) is remembered
  per gateway key, so one key cannot change how another key's requests are
  sent.
- The **media output cache is shared across keys**; see Known limits.

### Billing integrity

Usage is what budgets and invoices are built on, so a client must not be
able to lower its own bill.

- Token counts are read only from the places the protocols put usage
  (`usage.*` and its equivalents), never from matching text elsewhere in a
  response.
- A response that ends early is still billed: the provider's real figures
  if they can still be read within `OMNIGATE_ABORT_DRAIN_MS` after a client
  disconnects, otherwise an estimate marked as one.
- A media job is priced from what the adapter sent to the provider, not
  from labels in the client's input; every part of the price is at least
  zero; negative durations, counts and prices are refused.
- Job creation is rate-limited in the control plane as well as the data
  plane, the number of unfinished jobs per key is capped, and so is the
  size of a job's input.
- Usage events are deduplicated by request id, so a resent batch never
  bills twice.

### Files and webhooks

- Outputs on local disk are served through URLs signed with HMAC-SHA256 that
  expire (one hour by default), or to the gateway key that owns the job.
  The signing key is `OMNIGATE_SIGNING_SECRET`, or is derived from the
  internal token.
- A stored output is bytes a provider produced. The control plane serves it
  as a download (`Content-Disposition: attachment`) with `nosniff` and a
  sandboxing `Content-Security-Policy`, and keeps its declared type only
  when that is one of a short list of image, video and audio types;
  anything else, HTML and SVG included, goes out as
  `application/octet-stream`. The data plane passes those headers on to
  the client; of a control-plane answer it relays a fixed list (the four
  file headers, `retry-after` and `location`) and nothing else.
- Outputs in a bucket are assumed private and handed out as presigned URLs.
- Webhooks are signed the [Standard Webhooks](https://www.standardwebhooks.com/)
  way (HMAC-SHA256 over id, timestamp and body). Receivers should verify the
  signature and the timestamp; see [docs/api.md](docs/api.md#webhooks).
- **URLs that somebody else chose are not trusted.** A client's webhook URL
  and the output URLs in a provider's answer go through the same check.
  They must be http(s), without embedded credentials, and must resolve only
  to public addresses unless `media.webhooks.allow_private` is set:
  loopback, private, link-local, carrier NAT, documentation, benchmarking
  and multicast ranges are refused, and so are the IPv6 forms that carry an
  IPv4 address inside (mapped, compatible, NAT64, 6to4, Teredo). The host
  is resolved once, every resulting address is checked, and the connection
  is made to the checked address, so a DNS answer that changes between the
  check and the call (DNS rebinding) cannot point it at an internal
  address. Webhook deliveries do not follow redirects; output downloads
  follow at most five, each hop checked the same way.

### Resource limits

On the public port:

- A request head may be at most 16 KiB with at most 100 header lines, and a
  request body at most 8 MiB, nested at most 64 levels deep.
- A client that does not finish sending a request, or leaves a connection
  idle, is disconnected after `OMNIGATE_CLIENT_TIMEOUT_MS` (30 seconds).
- A response that stops moving, because the upstream went silent or the
  client stopped reading, is cut off after
  `OMNIGATE_STREAM_IDLE_TIMEOUT_MS` (5 minutes). That includes the
  gateway's own answers and file downloads.
- At most `OMNIGATE_MAX_CONNECTIONS` (4096) connections are served at once;
  further ones get an immediate 503.
- Requests the gateway refuses are counted per key name and reason, with a
  cap on the number of distinct series, so a flood of made-up keys cannot
  grow memory. The table of learned model quirks is capped as well.

On the control plane:

- A job's `input` and `metadata` may be at most `media.max_input_bytes`
  (1 MiB) together, and a key may have at most `max_open_jobs` (100)
  unfinished jobs.
- An anonymous request body is limited to 4,096 bytes; any other body is
  read only after the credential check, up to 8,000,000 bytes.
- The table of failed attempts is swept once it has grown, so guesses from
  many addresses cannot fill memory.

These bound what one client can hold; they are not a defence against a
volumetric attack. Put the data plane behind a proxy or load balancer that
you would trust with that.

### What must stay private

- The control plane's port. Expose the dashboard only through a TLS proxy
  that refuses `/internal/*` from outside, as `deploy/Caddyfile` does, and
  preferably only to the addresses of your operators
  (`OMNIGATE_ADMIN_ALLOW`).
- Both tokens; the files `.env.control` and `.env.dataplane`; and the
  config file if it holds raw keys or inline webhook secrets. (`.env` now
  holds only host names and the allow-list, unless you kept secrets in it
  from an earlier commit.)
- The control plane's data directory: the ledger files (`ledger.jsonl`,
  its sealed segments and its two snapshots) and `jobs.jsonl` (usage per
  key; job inputs, metadata and webhook URLs), `keys.json` (key hashes, and
  the webhook secret of any managed key that has one, in clear text),
  `audit.jsonl` and its rotated files (who did what, from which address),
  and the media directory or bucket. Backups of it are as sensitive.
- The control plane's log, if you let it generate the admin token.

The data plane's access log holds key **names**, route names and request
paths, never keys, key hashes, request bodies or query strings (a signed
file URL's query string is a credential). Client-supplied text in it has
control bytes escaped.

Details: [docs/deployment.md](docs/deployment.md#what-to-keep-private) and
[docs/security.md](docs/security.md).

## Known limits

These come from the code and from the README's
[Known limits](README.md#known-limits) section. They are known, not
vulnerabilities to report.

- **No TLS listener on either process.** The included Caddy proxy (or
  another) provides it. Data-plane-to-control-plane traffic over HTTPS is
  untested; keep it on a private network.
- **One shared admin token.** No user accounts or roles, so the audit log
  can say how a caller was authenticated and from which address, not who
  they were. Sessions cannot be revoked individually; changing the token
  ends all of them. Whoever holds the token can create gateway keys.
- **The audit log is a plain file** the control plane appends to. It is not
  tamper-evident, and someone who can write to the data directory can
  change it. If a line cannot be written, the action still goes ahead (and
  an error is logged). Reads of the admin API are not recorded, and neither
  are requests refused for a missing or wrong token (the bearer lockout
  included) or a missing CSRF token. The file is rotated by size and only
  three older files are kept, so old entries are eventually deleted; copy
  it elsewhere if you need a longer record.
- **A managed key's webhook secret is stored in clear text** in `keys.json`,
  because signing needs the secret itself.
- **The lockouts count per client address and live in memory.** A restart
  forgets them. Behind a reverse proxy all clients share the proxy's
  address unless `OMNIGATE_TRUST_FORWARDED` is set, and then the proxy must
  be the only way in. A lockout is also a lever: 20 wrong bearer tokens
  from an address your own automation shares stop that automation for the
  rest of the minute.
- **The admin allow-list is a proxy rule**, not something the control plane
  enforces, and it judges the address the proxy sees. Behind another proxy
  or Docker Desktop's network that is not the client's address.
- **Estimated usage is an estimate.** A stream that ends without the
  provider's closing figures is billed from the size of the request and
  the number of events received. It is meant to be close, not exact. The
  mark (`estimated`) is in the ledger line, in the text access log and,
  for the newest requests, in `GET /admin/overview`; the dashboard page,
  the metrics and the JSON access log do not show it.
- **Strictness has a cost.** Paths with percent-encoding or a trailing
  slash, unusual query characters and deeply nested JSON are refused. A
  client that sent them to an earlier commit and was served now gets `400`.
- **Budgets are enforced after the fact**, with up to one poll interval of
  lag, and cannot newly block a key during a control-plane outage. A
  monthly or daily budget unblocks by itself when its UTC period turns; a
  total budget never resets.
- **The internal token is as powerful as every gateway key together.** On
  `/internal/*` it reads the config snapshot (key hashes, upstream
  addresses), writes usage events, and acts as any gateway key on the jobs
  API. Keep the control plane's port private. The data plane, which faces
  the internet, necessarily holds it.
- **Key changes take effect at the next config poll**, a couple of seconds
  by default. A data plane that cannot reach the control plane keeps
  accepting a key that was revoked in the meantime, until it can poll
  again.
- **Rate limits live in memory.** For text requests they are per
  data-plane process, so several data planes each allow the full limit;
  job creation is counted once more in the control plane. Both reset on a
  restart of the process that holds them.
- **Duplicate-detection ids expire** (14 days by default). A usage event
  that a data plane resends later than that would be counted twice.
- **The media output cache is shared across gateway keys.** An identical
  cacheable job request from another key reuses the stored output.
- **Output downloads send no provider credentials**, so an output URL that
  can only be fetched with the provider's API key cannot be stored.
- **Refusal counts and the access log are for diagnosis, not for audit**:
  the counts are best effort and kept in memory only.
- **The hostile-input fixes have been tested, not attacked.** They are
  covered by unit and fuzz tests, `tools/malformed_test.py` and the
  container test, all written by the project. There has been no external
  penetration test.
- **Nothing has run under production load.**

## Past advisories

No release has been tagged, so these are identified by commit. All of them
were found by an independent review of the code in November 2026, by
reading and small proofs of concept. **None is known to have been
exploited.**

|---|---|---|---|

### Authentication bypass on the control plane through percent-encoded paths

Fixed in commit 97cf396 (November 2026).

**What was wrong.** The control plane's credential checks compared the
request path as it was sent, while its router matched the percent-decoded
path. A request whose first path segment was written with an encoded
character (`/%61dmin/keys` for `/admin/keys`, `/%69nternal/config`,
`/%6Detrics`) was not recognised by the admin-token check, the
internal-token check or the CSRF check, and still reached the handler.

**What it allowed.** Anyone who could send HTTP requests to the control
plane, without any credential, could:

- use the whole admin API: list keys and usage, create, change, disable,
  rotate and delete managed gateway keys, read the overview and the audit
  log;
- read `/metrics`;
- use `/internal/*`: read the config snapshot (key hashes, upstream names
  and addresses), write usage events into the ledger, and read, create and
  cancel media jobs as any gateway key.

It did not reveal the admin token, the internal token or any provider key;
no endpoint returns those.

**Who was affected.** Every commit before 97cf396 that has an admin token
(before commit c53acd6 the admin API had no authentication at all), if the
control plane's port could be reached by someone you do not trust. That
includes the Compose deployment when the dashboard's host name was
reachable from outside: the included proxy forwards the dashboard host's
requests to the control plane as they are, so it was no protection for the
admin API. A control plane bound to loopback or reachable only from a
trusted network was not exposed. The data plane's port was not a way in
through this bug: it forwards only `/v1/jobs*` and `/v1/files/*`.

**What to do.**

1. Update the control plane to 97cf396 or later (3a0b147 or later to have
   the other fixes on this page too).
2. Set a new `OMNIGATE_ADMIN_TOKEN`. The bypass did not reveal it, but
   until commit 3a0b147 wrong bearer tokens could be guessed without any
   throttle and a short token was only warned about, so a token that was
   exposed to the internet for a while should not be kept.
3. List the keys (`GET /admin/keys`) and delete any managed key you did not
   create. Rotate the managed keys you want to keep if they were created or
   rotated while the control plane was exposed.
4. Look through the audit log (it exists from commit 5450398 on) for
   `key.create`, `key.update`, `key.rotate` or `key.delete` entries with
   `"auth": "none"`. Such an entry could only be produced through this
   bypass. Reads were never recorded, so a clean log shows that no key was
   changed this way, not that nobody looked.
5. Treat what the snapshot and the admin API show as disclosed for that
   period: key names and hashes, usage figures, upstream addresses, and
   recent jobs with their signed output links. A generated key cannot be
   recovered from its hash; replace any short or guessable key you wrote
   into the config file yourself.
6. If spend figures from that period matter, remember that usage events
   could have been written without a credential.

**The fix.** A path with any encoded character is refused with `400` before
routing (no route needs one); the checks deny by default, so an unknown
first path segment is a `404` instead of being passed to the router; and
credentials are checked before the body is parsed. Regression tests cover
it at the unit level, in the end-to-end test and, byte for byte through the
TLS proxy, in the container test.

### Remote crashes of the data plane

Fixed in commit fde530c (November 2026).

**What was wrong.** The data plane serves every connection from one
process, and a panic in any connection's task ends that process. Three
inputs reached code in Zig's standard library that asserts on their shape:

- a request head with a header line that has no colon (the header iterator
  unwrapped a null). No key needed; one request.
- a `POST` or `PUT` with neither `Content-Length` nor chunked encoding (the
  body reader asserted). No key needed; one request.
- a JSON body nested 256 levels deep or more (the serialiser indexes past a
  fixed stack). A valid gateway key was needed, since the body is parsed
  after authentication.

**What it allowed.** Anyone who could reach the gateway's port could end
the process with a single request, as often as they liked: every request in
flight was dropped, and with them the state the data plane keeps only in
memory (rate-limit buckets, cooldowns, the response cache, refusal counts
not yet reported). Nothing was disclosed and nothing was written. Usage
already queued was in the spool file and was delivered after the restart,
unless the spool was switched off.

**Who was affected.** Every commit before fde530c. The data plane is the
port that is meant to be public, so assume every deployment. A proxy in
front, the included Caddy one among them, parses and rewrites a request
head before the gateway sees it, which may have kept the first two away
from the gateway; that was not established for every form, and deeply
nested JSON is a well-formed request that any proxy passes on. Do not
count on the proxy.

**What to do.** Update the data plane to fde530c or later. There is nothing
to rotate. If your data-plane container restarted for no reason you could
find, this may have been why; the logs of that time would show a panic
rather than a clean stop.

**The fix.** Request heads are validated by code that cannot panic before
anything else reads them, and the gateway's own header iterator replaces
the standard library's; nesting is bounded (64 levels from a client, 128
from an upstream) before any parse; provider numbers saturate instead of
overflowing. A panic, should one still happen, logs one line and exits
with status 70. `tools/malformed_test.py` replays these requests and a few
hundred generated variations and checks after each that the gateway still
answers; fuzz tests in the translation and usage code feed them malformed
values by the thousand.

### Request smuggling and header injection into the internal API

Fixed in commit fde530c (November 2026).

**What was wrong.** For `/v1/jobs*` and `/v1/files/*` the data plane
forwards the client's request to the control plane's internal API, adding
the internal token. It built that request by pasting the client's request
target into a URL string, and it copied the client's `Idempotency-Key`
header as it was. The standard library's parser accepts a request line that
contains bare line feeds, so a "target" could carry line breaks and with
them a second request; a header value could carry a line break and with it
a second header.

**What it allowed.**

- A second request of the caller's choosing to `/internal/*`, sent by the
  gateway on the same connection and completed by the gateway's own
  headers, the internal token among them. The case the regression test
  replays is a batch of usage events for an arbitrary key hash, which the
  ledger would have recorded as that key's spend.
- Extra header lines of the caller's choosing on the forwarded request,
  through a line break in `Idempotency-Key`. The regression test uses
  `x-omnigate-key-sha256`, the header that tells the control plane which
  gateway key a job request belongs to.
- The internal token itself was not disclosed: the gateway relays one
  answer per client request and then closes its connection to the control
  plane.

How far either could be taken was not worked out in full. Treat the
internal API (the config snapshot, usage intake, the jobs API as any key)
as having been reachable, with the gateway's token, to whoever could send
such requests.

**Who was affected.** Every commit before fde530c with the data plane
reachable by a party you do not trust. Job requests are authenticated
before they are forwarded, and the regression test uses a valid gateway
key. Signed file URLs are forwarded without a key and went through the same
code; assume that path was open too. A proxy in front that parses request
heads itself (the included Caddy one does) is not expected to pass the
bare-line-feed form on as it was sent, but that was not verified for every
variant.

**What to do.** Update the data plane. If parties you do not fully trust
held gateway keys, or the data plane's port was reachable directly, look at
the usage recorded for that period before you bill from it: events could
have been written under any key. There is nothing to rotate for this alone.

**The fix.** A request head with a bare line feed, a control byte or a
malformed line is refused before use. The path must be in canonical form
and the query string plain, and both are set as components of a URL parsed
from the gateway's own configuration instead of being spliced into a
string. Header values the gateway copies (`Idempotency-Key`,
`anthropic-version`, `anthropic-beta`) are restricted to small character
sets. After an answer that was sent before the body was read, the
connection is closed, so that an unread body can never be parsed as the
next request.

### Billing evasion

Fixed in commits fde530c (data plane) and 3a0b147 (control plane),
November 2026. Each of these let the holder of a gateway key cause provider
cost that the ledger did not record, or recorded too low.

**What was wrong.**

- **Abandoned streams were free.** When a client disconnected mid-stream
  the gateway billed what it had metered so far. OpenAI-style providers
  send usage as the last event, so a client that hung up just before the
  end was usually billed nothing, while the provider charged for the whole
  generation.
- **Token counts were found by text search.** The usage scanner looked for
  `"prompt_tokens":` and similar anywhere in the response bytes. Text a
  client could get echoed into a response, such as a tool schema or a tool
  call's arguments, could therefore change that client's own bill.
- **Media jobs were priced from the client's labels.** A per-second price
  was multiplied by `input.duration` as written, so a negative duration
  reduced the price of the rest of the job; a per-character price used the
  first of `text`, `prompt` and `input` that was present, which need not be
  the field the provider read. A negative price in the config was accepted.
- **`/v1/jobs/` was not rate-limited.** The data plane recognised only the
  exact path `/v1/jobs` as a job creation, while the control plane also
  accepted the spelling with a trailing slash, so that spelling created
  jobs without counting against the key's `rpm`. There was also no limit on
  the number of unfinished jobs a key could hold, or on the size of a job's
  input.

**Who was affected.** Deployments that give gateway keys to parties they do
not fully trust and rely on the ledger for budgets or invoices. A key
holder gains unbilled usage of your provider accounts; nothing is
disclosed.

**What to do.** Update both processes. If it matters, compare the ledger
with your providers' invoices for the period before the update; the
difference cannot be reconstructed from the gateway's files. Expect bills
to change after the update: abandoned streams now cost something, and
per-second and per-character media prices follow what is sent to the
provider. There is nothing to rotate.

**The fix.**

- A stream the client leaves is read on for up to
  `OMNIGATE_ABORT_DRAIN_MS` to get the provider's real figures; without
  them the call is billed an estimate (never below what was metered) and
  marked `estimated`.
- The usage reader is a JSON tokenizer that counts a number only at the
  paths the protocols define.
- Each media adapter reports the characters and seconds in the request it
  builds, every component of the price is clamped at zero, negative
  durations and counts are refused with `400`, and a negative price stops
  the config from loading.
- One canonical spelling per path in the data plane; the control plane
  rate-limits job creation itself, caps unfinished jobs per key
  (`max_open_jobs`) and the size of a job's input
  (`media.max_input_bytes`).

### Server-side request forgery through provider outputs

Fixed in commit 3a0b147 (November 2026).

**What was wrong.** When a media job finishes, the control plane downloads
each output from the URL in the provider's answer and stores it. Those URLs
were fetched as given, with the HTTP client following redirects by itself
and no check on where they led. Webhook URLs were already checked, but
against a shorter list of private ranges that missed several IPv6 forms
carrying an IPv4 address (NAT64, 6to4, IPv4-compatible) and some
special-purpose IPv4 ranges.

**What it allowed.** If a provider's answer could be made to contain a URL
of someone's choosing, or a URL that redirects, the control plane would
fetch it from inside your network and store the response as the job's
output, which the job's owner can download. Depending on what the control
plane's host can reach, that is a way to read cloud metadata endpoints or
internal services. A provider's answer is only as trustworthy as the
provider and, where it hosts models written by third parties, as the model
that produced it.

**Who was affected.** Deployments before 3a0b147 with media routes, whose
control plane can reach internal HTTP services, and where untrusted parties
can create jobs or a configured provider is not fully trusted. Text-only
deployments were not affected.

**What to do.** Update the control plane. If the conditions above applied,
look through stored outputs of the period for files that are not media (a
job's `content_type` and size are in `jobs.jsonl`), and rotate any
credential an internal endpoint would have handed out, instance-metadata
credentials first. Keep `media.webhooks.allow_private` off.

**The fix.** Output URLs go through the same guard as webhook URLs: the
host is resolved once, every address is checked, the connection goes to the
checked address, and redirects are followed by the control plane itself,
at most five, with the check repeated on every hop. The list of refused
addresses now follows the IANA special-purpose registries for IPv4 and
IPv6.

### Other hardening from the same review

Commits fde530c and 3a0b147. Smaller findings, fixed together with the
above. None needs action beyond updating, except where noted.

- **Stored outputs were served inline.** A provider-produced file with an
  HTML or SVG type was served as that type from the gateway's own origin.
  Outputs are now served as downloads with `nosniff` and a sandboxing
  `Content-Security-Policy`, and only a short list of media types keep
  their type. (Between commits 3a0b147 and 10bc009 the data plane did not
  pass those headers on and the included proxy added them; since 10bc009
  the gateway sends them itself.)
- **Wrong admin bearer tokens were not throttled**, only failed sign-ins
  were, and a short admin token only produced a warning. Now 20 wrong
  tokens per address per minute lock the address out, and a token under 16
  characters stops the start. **Action:** make sure yours is long enough
  before you update.
- **Both containers shared one environment file**, so the internet-facing
  data plane held the admin token, media provider keys, webhook secrets
  and bucket credentials. Compose now gives each container its own file.
  **Action:** split your `.env`
  ([docs/deployment.md](docs/deployment.md#coming-from-a-commit-before-3a0b147)).
- **A release build without `OMNIGATE_CONFIG` fell back to the development
  config**, whose gateway keys and webhook secret are published in this
  repository. A release now refuses to start without the variable.
- **Learned provider quirks were shared across gateway keys.** One key
  could make the gateway strip sampling parameters from every other key's
  translated requests to the same model. They are now remembered per key.
- **Client text could forge log lines.** A model name with a line break
  started a new line in the text access log. Control bytes are now
  escaped, and a signed URL's query string is never logged.
- **An early answer could be lost.** After refusing a request before
  reading its body (a bad key on a `POST`), closing the socket could reset
  the connection before the client had read the 401. The gateway now
  closes politely.
- **The dashboard host could not be restricted by source address** without
  editing the proxy configuration. `OMNIGATE_ADMIN_ALLOW` does it.
- **Ledger snapshots are shape-checked** row by row before use (the
  checksum catches accidents, not tampering), and the control plane's
  listener is HTTP/1.1 only.
- **Duplicate-detection ids were kept for ever**, growing memory and
  snapshots with every request served. They now expire after 14 days by
  default.
